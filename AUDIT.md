Legend: 🔴 critical · 🟠 high · 🟡 medium · ⚪ low / hygiene

Resolution this changeset: the 🔴 unmetered-`judge` and 🟠 `spend_llm`

## The app in one pass

A job enters one of seven doors (`runBoards`, `runAts`, `addSuggested`, `onCsv`,
`pasteJobDialog`, `coldDialog`, `importBackup`) and everything except backup
converges on `addJobs` → `keyOf` (identity) → `autoScore` (`index.html:2138`,
`2133`, `2376`). Board search is the only door that scores on the way in; the
rest are scored later against the CV by DeepSeek in batches of 12
(`scoreBatch`, `index.html:2299`).

Every job lives inside one JSON blob per user — `public.user_state` is a single
`text` column keyed by `(user_id, k)` (`schema.sql:11`). A save is a full
rewrite of that blob (`save`, `index.html:877`), written locally first, then
upserted to Supabase (`put`, `index.html:846`). Rendering turns a scored job
into one row with at most one accent via the closing→strong→worth cascade
(`index.html:3031`, `3023`).

The edge function (`supabase/functions/api/index.ts`) is a credential broker and
meter: it holds the DeepSeek/Apify/Razorpay/TypeSafe keys, charges credits
before each paid call, and refunds on upstream failure. The ledger is
`usage_events` (`billing.sql:167`).

## Security

### 🟠 Service-role key bypasses RLS — the auth gate is the only scope
`supabase/functions/api/index.ts:48`, `428`. `admin` is built from
`SUPABASE_SERVICE_ROLE_KEY`, so every query skips row-level security; the single
thing scoping any query is `user = auth.user.id` taken from `getUser`. One action
that forgets to filter by `user` becomes a cross-user data leak. Audit all 11
actions for a `user` predicate on every read/write.

### 🟡 `judge` forwards candidate PII to a second vendor
`supabase/functions/api/index.ts:634`. The new Jev call sends `posting` +
`candidate` (name, location, strengths, gaps, wrong shapes) to TypeSafe. That
was already true for DeepSeek scoring, but it is now a second data processor;
worth a line in your privacy/terms copy.

### ⚪ Browser-held user keys sit in localStorage
`index.html:823` (`LOCAL_ONLY`), `875`. The user's own DeepSeek/Anthropic/Apify
keys are kept off the cloud but live in `localStorage`, readable by any script
on the page. Verify there is no XSS surface (and consider a CSP) before calling
that acceptable.

## Data integrity

### 🔴 Whole-blob last-writer-wins loses concurrent edits
`schema.sql:11`, `index.html:877`. A new job is a full rewrite of the one
`user_state` text blob, not a row insert. Two tabs searching at once silently
lose one tab's work. This is already acknowledged in the pipeline map
(`st.blob`), but it is the highest-impact data bug in the app.

### 🟡 `logUsage` swallows its own failures
`supabase/functions/api/index.ts:332-335`. `if (error) console.error(...)` means
the cost ledger can silently stop recording and nobody notices. The `llm` action
even documents a case where a missing column would make the ledger drop rows
silently. Surface this (count of failed writes, or an alert) rather than
logging only.

## Cost & abuse

### 🔴 The `llm` action now runs at a loss (measured 2026-09-24)
`supabase/functions/api/index.ts` `COST.llm`. Against `usage_events`, a DeepSeek
call costs **₹1.15-1.21**; one credit sells for **₹0.80-0.99**. It was ~₹0.07
until 2026-09-22, when gating reasoning to `pro` and lifting `TOK_CAP` to 16000
took average output from ~310 to ~3300 tokens — an 18x jump, correct in itself
and the fix for a real truncation bug, but nobody repriced afterwards. Worse on
the Pro pack than the Starter. 12 of 45 calls carry no `search_id`, so they are
manual rescores and drafts, at ₹1.31 each. Either raise `COST.llm`, cut what a
call is asked to generate, or route intake to `flash`.

### 🟢 Sources re-cut from the ledger (2026-09-24)
**LinkedIn** cost ₹13.20 of a ₹16-18 search for 5 exclusive 50+ jobs (₹7.66
each) and was demoted `core` -> `probe`. `PRICE_USD.linkedin` is a **guess** —
bebity publishes no price — so ₹7.66 is a floor, not a figure.

**Naukri** had never completed a run: `Apify 400 Maximum cost per run is less
than the allowed minimum of $0.40` against a global `SCRAPE_MAX_USD = 0.15`,
for ten days, while `FREE_SCRAPERS` and `pricing.html` both sold the free tier
as "LinkedIn, Indeed and Naukri". The cap is now per-scraper and Naukri's is
`$0.40`. That is the actor's floor for the *ceiling*, not a charge: it bills a
start fee plus ~$1/1,000 results. Read the real number off `usage_events`.

**JSearch** was deleted and then restored the same day, on
`api.openwebninja.com/jsearch/search-v2` (vendor-direct, ~30% under the RapidAPI
listing) after the old `/search` path 404'd. It reads Google for Jobs, so it
covers LinkedIn, Indeed, Glassdoor, ZipRecruiter and more in one request per
title with full descriptions, at roughly a quarter of what the LinkedIn scraper
cost. **It requires an OpenWeb Ninja key**; the old RapidAPI value in
`JSEARCH_API_KEY` will 401. It does **not** cover Naukri.

⚠ Two things here are unverified until a real key runs: whether `/search-v2`
returns its jobs as a bare `data` array or wraps it (the mapper accepts both),
and JSearch's actual yield, which has never been measured because it has never
once succeeded.


### 🔴 New `judge` action is unmetered and unbounded
`supabase/functions/api/index.ts:634`. I added it free on purpose, but as it
stands any authenticated user can call it unlimited times and burn the
operator's TypeSafe budget. It has no `spend`, no ledger row, no rate limit, and
no cap on `posting`/`candidate` size. Give it a credit cost (or a per-call
ceiling) before it reaches the scoring hot path.

### 🟠 `spend_llm` free branch undercharges by construction
`billing.sql:78`. The free branch decrements `free_llm` by **1** regardless of
`p_n`. Harmless only because `COST.llm === 1` today; any larger cost silently
undercharges. Make it decrement `p_n`, or assert `p_n = 1` in the function.

### 🟡 Free-tier comment has drifted from the value
`billing.sql:12` says `free_search default 5`; `billing.sql:100` says "16th board
search: the free tier is over." One of these is wrong. Fix the comment so the
free tier is not a guessing game.

## Reliability & observability

### 🟡 `grabJSON` is fragile string surgery on model output
`index.html:1761`. It does `indexOf('{')`/`lastIndexOf('}')`, strips fences, then
whitelists flags and still reads "old long names in case the model uses them."
This is the exact brittle layer Jev is meant to replace for the classifier
fields — migrate `c`/`f` first, and keep only the free-text fields (`why`) on the
string path.

### 🟡 Prompt-cache contract is unguarded
`index.html:2069`. "Nothing variable may go before JOBS TO SCORE" is load-bearing
for DeepSeek prompt-cache pricing — a prefix change silently doubles cost with no
error. Add a test or a comment-anchor check that the stable prefix is stable.

### ⚪ `judge` returns the upstream error string to the browser
`supabase/functions/api/index.ts:640`. `Judgment call failed: ${msg.slice(0,140)}`
leaks internal details. Return a fixed message and log the detail server-side.

## Scoring correctness

### 🟡 Confidence is ordinal but `rankOf` needs a number
`index.html:2148`. `rankOf` is `fit^0.65 × reach^0.35 × confidence`, yet
confidence arrives as `h|m|l`. Somewhere a mapping turns that into a number;
if confidence moves to Jev as a 3-way `choice`, that mapping must be preserved
explicitly, or ranking silently changes.

### 🟡 Jev flag list is a second source of truth
`supabase/functions/_shared/judge.ts` vs `index.html` `FLAG_CODES`. The ten flag
codes now live in two places. Add a check (or a shared constant) so they cannot
drift.

## The new Jev/TypeSafe path

- `judge` is deployed (`api`) and type-checked, but **not wired into scoring**
  yet — `judgeJob()` exists in `index.html` but `scoreBatch` still takes `c`/`f`
  from DeepSeek. That is the intended next step, not a defect.
- Jev defaults to `jev-latest` (SDK). "latest" can change behavior and price
  silently; pin a model when the integration is real.
- The one-line `why` and the continuous fit/reach scores cannot move to Jev
  (typed judgments, no free text, ordered levels not 0–100) — they stay on
  DeepSeek by design.

## Decisions & learnings (recall at the end)

- **The matcher's "why" is keywords, not a sentence.** Classification output
  should be structured: flags + extracted facts + evidence spans + numeric
  scores. A human sentence is a UI/render concern only — templated from the
  keywords, never returned by the model. Consequence: the whole classifier can
  be typed (Jev for flags/confidence, numeric for fit/reach), and the free-text
  `why` field drops out of the model output entirely. This is the last reason
  DeepSeek stayed in the classification loop; removing it removes DeepSeek from
  classification.
- **Moat = evidence, not prose.** The anti-LinkedIn transparency is showing the
  flag + the fact + the quoted span from the posting, in both directions
  (candidate sees "why this job", employer sees "why this candidate").
- **Product thesis: match on the work, not the network.** Fit (can they do it)
  vs reach (will they actually get it), separated, with a shown reason. One
  matcher, two client sides.
